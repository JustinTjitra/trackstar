## 1. Web Audio capture: getUserMedia constraints for clean stereo line input in Chrome

### Takeaway
Request `echoCancellation:false, noiseSuppression:false, autoGainControl:false, channelCount:2` (plus a `deviceId` for the virtual device) and then read back `track.getSettings()`, because Chrome treats these as requests and has a history of silently returning mono or a different sample rate. With all three processing flags off, Chrome reportedly delivers true 2-channel audio at the device rate; with echo cancellation on, the track is forced to 1 channel.

### Cited Findings
- To get true stereo from getUserMedia, a developer had to disable audio processing by setting `noiseSuppression`, `echoCancellation` and `autoGainControl` to false; some hardware still only yields duplicated mono (e.g. built-in MacBook mics expose 1 channel), and Audio MIDI Setup shows how many input channels a device really has (snippet) — [Addpipe blog](https://blog.addpipe.com/recording-true-stereo-audio-using-getusermedia/)
- When `echoCancellation` is true and `channelCount` is not explicitly 2, the audio track's channelCount is always 1; the recommended recipe is explicit `channelCount: 2` with `echoCancellation: false` (snippet) — [discuss-webrtc thread](https://groups.google.com/g/discuss-webrtc/c/ZoqwOw6ZjPg)
- A report on the W3C WebRTC list says that with `echoCancellation:false` Chrome returned `channelCount` 2 and `sampleRate` 44100 even when 1 and 48000 were explicitly requested, i.e. with processing off Chrome passes through the device's native format and ignores channelCount/sampleRate constraints (snippet) — [public-webrtc-logs, Apr 2023](https://lists.w3.org/Archives/Public/public-webrtc-logs/2023Apr/0082.html)
- Chromium's tracker notes that since M73 `channelCount` can be specified via constraints for multichannel capture (snippet; page not readable from here) — [Chromium issue 40403559](https://issues.chromium.org/issues/40403559)
- Historical behaviour (2015-16, treat as background only): if echo cancellation was not disabled, stereo input was merged to mono and then duplicated into two identical channels (snippet) — [public-audio list, Hongchan Choi](https://lists.w3.org/Archives/Public/public-audio/2016JanMar/0001.html)
- `latency` is a defined audio constraint (ConstrainDouble, in seconds) and `MediaTrackSettings.latency` reports what was applied, but MDN marks it as not Baseline (not supported in some major browsers); feature-detect with `navigator.mediaDevices.getSupportedConstraints().latency` (snippet) — [MDN MediaTrackConstraints.latency](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/latency), [MDN MediaTrackSettings.latency](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackSettings/latency)
- On macOS Chrome, the reported track latency multiplied by the sample rate came out near 128 regardless of sample rate; the poster concluded the number reflects an internal buffer size, not the true input path latency (snippet) — [chromium-dev thread](https://groups.google.com/a/chromium.org/g/chromium-dev/c/YCywOaFTSm8)
- No JS API reports true end-to-end input latency; the only reliable method is a loopback measurement (play a click, capture it, compare timestamps) (snippet, low-authority tool-vendor pages) — [probecheck.com](https://probecheck.com/audio-latency-test/), [soundlatencytest.com FAQ](https://soundlatencytest.com/faq/)

### Inferences
- Suggested constraint object (synthesised from the findings above, untested): `{audio: {deviceId: {exact: blackholeId}, echoCancellation: false, noiseSuppression: false, autoGainControl: false, channelCount: {ideal: 2}, sampleRate: {ideal: 48000}, latency: {ideal: 0}}}`. Use `ideal` rather than `exact` for anything other than deviceId so the call does not reject with OverconstrainedError; then assert `getSettings().channelCount === 2` and compare `getSettings().sampleRate` with `audioContext.sampleRate`.
- Because Chrome appears to pass through the device's native rate when processing is off, the practical way to avoid resampling is to set the virtual device, the FLX2 and the AudioContext (`new AudioContext({sampleRate})`) to the same rate in Audio MIDI Setup, not to rely on the `sampleRate` constraint.
- A virtual loopback device (BlackHole 2ch) is a genuine 2-channel device, so the "duplicated mono" hardware pitfall should not apply; the remaining mono risk is a processing flag left on (or a Chrome default changing). A cheap runtime guard is to compute L-R energy in the worklet and warn if it is exactly zero on stereo material.
- The capture device and the output device (FLX2) are different clock domains unless they are bound in one Aggregate Device; Chrome must bridge them with a FIFO/resampler, which is a plausible source of both extra latency and slow drift glitches. This is an inference; no source found quantifies Chrome's behaviour here.

### Gaps
- Could not read the Chromium issue or Chrome docs to confirm current (Chrome 15x) defaults, e.g. whether macOS system voice-processing (VPIO) is ever engaged when all flags are false, or the maximum input channel count.
- A search summary stated that Chrome returns 0.01 s as a fallback for `getSettings().latency` regardless of hardware; I could not attribute this to a specific page, so treat as unverified.
- Whether Chrome honours the `latency` constraint for capture on macOS (i.e. actually shrinks the input buffer) is unverified.
- Device labels and stable deviceIds from `enumerateDevices()` require a granted mic permission; this is standard behaviour but was not sourced here.

## 2. Web Audio output: latencyHint, baseLatency, outputLatency, setSinkId, multi-channel output

### Takeaway
`AudioContext.setSinkId()` and the `sinkId` constructor option shipped in Chrome 110 (so also Chromium Edge), which lets the page send its output to the FLX2 specifically while capturing from a different device. `latencyHint:'interactive'` (the default) already asks for the smallest buffer; `baseLatency` and `outputLatency` are estimates of buffer sizes, not measurements of the real path. Addressing channels 3-4 of a 4-channel device is possible in the spec (raise `destination.channelCount` to `maxChannelCount`, discrete interpretation, ChannelMerger), but Chrome/macOS has historical reports of exposing only 2 channels, so it must be verified on the actual FLX2; for this project only channels 1-2 (master) are needed, which is the default.

### Cited Findings
- `AudioContext.setSinkId()` is available in Chrome 110 or later; the device id can also be passed at construction as `new AudioContext({sinkId})`; `setSinkId({type:'none'})` gives a silent sink; feature-detect with `'setSinkId' in AudioContext.prototype` (snippet) — [Chrome for Developers: Change the destination output device in Web Audio](https://developer.chrome.com/blog/audiocontext-setsinkid)
- `setSinkId()` rejects with `InvalidAccessError` if the id matches no device, and can be blocked by the `speaker-selection` Permissions Policy (snippet) — [MDN AudioContext.setSinkId()](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/setSinkId)
- `latencyHint` defaults to `'interactive'`, described as the lowest latency that does not cause glitches; the browser may or may not honour a requested value, and `baseLatency` must be read afterwards to learn what was actually chosen (snippet) — [MDN AudioContext() constructor](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/AudioContext)
- Definitions from the spec editor: `baseLatency` tells you whether the Web Audio implementation buffers internally; `outputLatency` is the latency induced by the OS/hardware; their sum is total output latency (useful for A/V sync) (fetched) — [WebAudio/web-audio-api issue 2467, padenot](https://github.com/WebAudio/web-audio-api/issues/2467)
- In Chrome, `baseLatency` "seems to match currentTime's increment interval" (i.e. one render quantum); Firefox `baseLatency` is "intentionally always zero" (2022) (fetched) — [web-audio-api issue 2467](https://github.com/WebAudio/web-audio-api/issues/2467)
- Chromium's Intent to Ship for `outputLatency` described it as the buffer size of the platform audio callback, with historical platform values "MacOS = 128 frames, Windows = 10ms, Android = 96 frames" (snippet; old thread) — [blink-dev: Intent to Ship AudioContext.outputLatency](https://groups.google.com/a/chromium.org/g/blink-dev/c/dTQniJNVVMY)
- Safari exposes `baseLatency` but not `outputLatency` (snippet, low-authority tool page) — [wutools.com latency tester](https://wutools.com/hardware/diagnostics/audio-latency-tester)
- Chrome 146 material lists a "Playback Statistics API for WebAudio" with latency statistics (only the page title was visible) — [Chrome platform showcase v146](https://chrome-platform-showcase.paulkinlan-ea.deno.net/v146/playback-statistics-api-for-webaudio/latency-stats/)
- `AudioDestinationNode.maxChannelCount` reports how many channels the physical device can handle (Baseline since April 2021) (snippet) — [MDN maxChannelCount](https://developer.mozilla.org/en-US/docs/Web/API/AudioDestinationNode/maxChannelCount)
- The multichannel design (2013): set `destination.channelCount` up to `maxChannelCount` to expose the hardware channels, and feed them with `ChannelMergerNode`s unless the source is already multichannel (snippet) — [public-audio-dev, Chris Rogers](https://lists.w3.org/Archives/Public/public-audio-dev/2013Mar/0012.html), [public-audio-dev, Chris Wilson](https://lists.w3.org/Archives/Public/public-audio-dev/2013Mar/0021.html)
- Counter-evidence (undated/old): a gist reports Chrome on macOS seeing only two output channels on multichannel USB interfaces, and an old Chromium review reports silence when destination channelCount exceeded 8 (snippet) — [colinbdclark gist](https://gist.github.com/colinbdclark/338ef0ecd7bccb9337caf978b9efb467), [Chromium code review 810763006](https://codereview.chromium.org/810763006)

### Inferences
- Minimal output setup (untested): `const ctx = new AudioContext({latencyHint: 'interactive', sampleRate: 48000, sinkId: flx2DeviceId});` then log `ctx.baseLatency`, `ctx.outputLatency`, `ctx.sampleRate`, `ctx.destination.maxChannelCount`. A numeric `latencyHint` (seconds) such as `0` or `0.003` is permitted by the API; whether it yields anything smaller than `'interactive'` on macOS Chrome is unverified, and the historical 128-frame callback figure suggests `'interactive'` is already at the floor.
- For channels 1-2 of the FLX2 nothing special is required: a stereo destination maps to the device's first two channels. To reach 3-4 the recipe would be `destination.channelCount = destination.maxChannelCount; destination.channelCountMode = 'explicit'; destination.channelInterpretation = 'discrete';` with a 4-input ChannelMerger. If `maxChannelCount` reports 2 for the FLX2, channels 3-4 are simply unreachable from the page.
- In the proposed design the browser never needs FLX2 channels 3-4 (rekordbox drives the headphone cue on them directly), so the channel-addressing uncertainty is not blocking.
- Edge is Chromium-based and should match Chrome's version numbers for these features; this was not separately sourced.

### Gaps
- Could not open Chrome Platform Status or MDN compat tables to confirm current Firefox/Safari support for `AudioContext.setSinkId` (as of my knowledge it was Chromium-only; unverified for late 2026).
- No source found for the actual `maxChannelCount` Chrome reports for a DDJ-FLX2/FLX4 on macOS.

- Whether changing sink at runtime rebuilds the audio graph with a glitch or a latency change was not found.

## 3. AudioWorklet: render quantum, renderSizeHint, round-trip latency, glitch risk, SharedArrayBuffer and cross-origin isolation

### Takeaway
The render quantum is 128 frames by default (2.9 ms at 44.1 kHz, 2.67 ms at 48 kHz). The configurable `renderSizeHint` option (Web Audio API 1.1) had an Intent to Ship for Chrome 153 on desktop and Android (July 2026) and one independent article reports using it in Chrome 153, measuring about 2.9 ms less loopback latency at 64 frames than at 128. The only hardware-measured macOS round-trip figure found is 19-23 ms through a Focusrite interface with a 128-frame buffer in both Chrome and Firefox; vendor/tool pages quote 10-35 ms. A plain AudioWorklet (JS or single-threaded WASM) needs no cross-origin isolation; only SharedArrayBuffer/WASM threads do, and GitHub Pages cannot send the required headers without a service-worker shim.

### Cited Findings
- The Web Audio API 1.1 spec gives a default render quantum of 128 frames, configurable via `renderSizeHint` (snippet) — [W3C Web Audio API 1.1](https://www.w3.org/TR/webaudio-1.1/)
- `renderSizeHint` accepts an integer, `"default"` (128) or `"hardware"`; it is a hint, and the value actually adopted must be read from `renderQuantumSize`; with `"hardware"`, `renderQuantumSize` returns 0 until the context is running (snippet) — [MDN AudioContext() constructor](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/AudioContext), [blink-dev Intent to Ship: WebAudio Configurable render quantum](https://groups.google.com/a/chromium.org/g/blink-dev/c/i4c1unRSmcE)
- Chromium's `"hardware"` hint currently always returns the default 128, partly for fingerprinting reasons; the origin trial was named `WebAudioConfigurableRenderQuantum`; the July 2026 Intent to Ship lists shipping in 153 on desktop and Android, with a comment that if the M153 launch slipped the trial would be allowed to expire (snippet) — [blink-dev Intent to Ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/i4c1unRSmcE)
- An article titled as measuring latency and CPU "since renderSizeHint was added in Chrome 153" found a 64-frame quantum gave a physical loopback round-trip about 2.90 ms shorter than 128 frames, and smaller quanta consistently gave shorter round-trips on the same I/O path (snippet; single author, single setup) — [Classmethod DevelopersIO](https://dev.classmethod.jp/en/articles/chrome-153-webaudio-render-size-hint-latency/)
- Measured: "On a Mac OS + Focusrite gen3 audio card, we measured 19-23ms on both chrome and FF, using a 128 sample audio buffer" (acoustic method: two mics into a hardware recorder, peaks compared in Audacity; includes ADC and DAC; no date given) (fetched) — [micbuffa/WAlatencyCompensation](https://github.com/micbuffa/WAlatencyCompensation)
- Tool-vendor claims (unsourced, inconsistent): desktop Chrome/Edge round-trip 18-35 ms on one page and 10-30 ms on another; Chrome `baseLatency` typically 2-4 ms (snippet) — [probecheck.com](https://probecheck.com/audio-latency-test/), [wutools.com](https://wutools.com/hardware/diagnostics/audio-latency-tester), [dev.to article](https://dev.to/dost_aid_4e09664efc68b805/web-audio-latency-is-quietly-ruining-your-reaction-test-537c)
- Chrome's AudioWorklet design-pattern article recommends a ring buffer (FIFO) to bridge block-size mismatches (e.g. WASM DSP that wants a different block size than 128) and describes two ways to get WASM into the worklet: load glue code inside AudioWorkletGlobalScope, or compile on the main thread and pass the module through AudioWorkletNode `processorOptions` (snippet) — [Chrome for Developers: Audio worklet design pattern](https://developer.chrome.com/blog/audio-worklet-design-pattern)
- `ringbuf.js` is a wait-free single-producer single-consumer ring buffer over SharedArrayBuffer with AudioWorklet examples (snippet) — [ringbuf.js on npm](https://npmjs.com/package/ringbuf.js)
- SharedArrayBuffer requires a secure context plus cross-origin isolation (COOP `same-origin`, COEP `require-corp`); check `crossOriginIsolated` at runtime (snippet) — [web.dev cross-origin isolation guide](https://web.dev/articles/cross-origin-isolation-guide), [CMU, R. Dannenberg blog on Web Audio + WASM](https://www.cs.cmu.edu/~rbd/blog/webaudiowasm/webaudiowasm-blog19oct2023.html)
- GitHub Pages does not allow custom response headers, so COOP/COEP cannot be set server-side; the standing feature request is still a community discussion, and the workaround (`coi-serviceworker`, which injects the headers from a service worker and reloads the page on first load) is reported to "cause a bunch of other problems" (snippet) — [GitHub community discussion 13309](https://github.com/orgs/community/discussions/13309), [Wasmer COOP/COEP how-to](https://docs.wasmer.io/javascript-sdk/how-to/coop-coep-headers)
- A WebKit bug reports SharedArrayBuffer apparently being copied rather than shared into AudioWorklet in Safari (unresolved in the snippet; irrelevant if Chrome/Edge only) — [WebKit bug 237144](https://bugs.webkit.org/show_bug.cgi?id=237144)

### Inferences
- Latency budget for this design (estimate, not measured): rekordbox's own output buffer is unchanged; added delay N = virtual-device transfer + Chrome capture buffering + cross-device FIFO + one render quantum (2.7-2.9 ms at 128) + Chrome output buffer + FLX2 DAC/USB buffer. The Focusrite 19-23 ms figure includes an ADC and analogue path that a virtual device does not have, so N of roughly 10-25 ms is a reasonable planning range for the browser insert, with `renderSizeHint: 64` buying back about 3 ms at higher underrun risk. This must be measured on the target Mac (digital loopback: rekordbox click -> BlackHole -> page -> second BlackHole -> recorder alongside the direct signal).
- Any effect that needs look-ahead (limiter, FFT/phase-vocoder with N-sample frames) adds its own algorithmic latency on top; time-domain filters, delays, flangers, bit-crushers and gates add none.
- Underrun risk factors to engineer around (general real-time practice, not individually sourced): allocation or GC inside `process()`, postMessage traffic into the worklet at high rate, a backgrounded or throttled tab, CPU frequency scaling on battery, Bluetooth output devices, and sample-rate mismatches forcing resamplers. Mitigations: preallocate, keep DSP in WASM or allocation-free JS, pass parameters with AudioParam or SharedArrayBuffer, keep the tab visible in its own window, run on mains power.
- Cross-origin isolation is only needed if the design uses SharedArrayBuffer (lock-free parameter/meter exchange, or WASM threads). A design that uses AudioParams plus occasional `port.postMessage` and single-threaded WASM runs on GitHub Pages with no header work. If SAB is wanted, either add `coi-serviceworker` or host on a platform that allows headers (Cloudflare Pages, Netlify, Vercel).
- getUserMedia needs a secure context; GitHub Pages serves HTTPS so this is satisfied (general platform knowledge, not sourced here).

### Gaps
- Could not open chromestatus.com or the blink-dev thread to confirm that `renderSizeHint` is in stable Chrome 153+ as of November 2026; the evidence is the Intent to Ship plus one article title. The permitted integer range and whether sizes below 128 are honoured on macOS are unverified.
- Could not read the Classmethod article's full table (hardware, baseLatency, CPU, glitch counts for 32/64/256).
- No measured round-trip for Chrome on macOS through a virtual device to a USB DJ controller was found; no published underrun statistics for AudioWorklet on Apple Silicon.
- No primary source located on the audio rendering thread's priority in Chrome on macOS (real-time vs normal priority).

## 4. macOS virtual audio routing: BlackHole, Loopback, Aggregate and Multi-Output devices, drift correction, and the step-by-step

### Takeaway
BlackHole 2ch (free, GPL-3.0, "zero additional driver latency") is the obvious virtual cable; Loopback (Rogue Amoeba, about $99) is the paid GUI alternative. There are two candidate topologies. Route A uses rekordbox's PC MASTER OUT, which is documented to work with a controller plus BlackHole but duplicates the dry master to the controller's own MASTER jack, so the processed signal must leave by a different physical output. Route B uses an Aggregate Device (FLX2 + BlackHole) selected as rekordbox's audio device so that master goes only to BlackHole and cue only to FLX2 3-4; Pioneer staff describe this pattern for generic interfaces, but it is unverified with an FLX2 attached.

### Cited Findings
- BlackHole: "licensed under GPL-3.0"; builds for 2, 16, 64, 128 and 256 channels (installer and Homebrew cover 2ch, 16ch, 64ch: `brew install blackhole-2ch`); sample rates 8 kHz to 768 kHz including 44.1 and 48 kHz; "Zero additional driver latency"; macOS 10.10+; Intel and Apple Silicon; build-time options `kNumber_Of_Channels`, `kSampleRates`, and `kLatency_Frame_Size` (adds delay, up to 65536 frames) (fetched) — [ExistentialAudio/BlackHole README](https://github.com/ExistentialAudio/BlackHole)
- BlackHole on Multi-Output devices: "You need to enable drift correction for all devices except the Clock Source also known as Master Device or Primary Device"; the Built-in Output must be enabled and listed top in a Multi-Output because of macOS issues (fetched) — [BlackHole README](https://github.com/ExistentialAudio/BlackHole)
- The "zero latency" claim is disputed by a Hacker News commenter for the Audio Server Plugin design (opinion, no measurement) (snippet) — [Hacker News thread](https://news.ycombinator.com/item?id=29621465)
- Apple: an Aggregate Device combines multiple audio devices into one; when devices are not hardware-synced, choose the device with the most reliable clock as Clock Source and enable Drift Correction (resampling) on the others; each device's sample rate should match the clock source's (snippet) — [Apple Support 102171](https://support.apple.com/en-mo/102171), [Audio MIDI Setup User Guide](https://support.apple.com/guide/audio-midi-setup/ams094c7edb4/mac)
- Apple's wording on whether the clock-source device itself should have drift correction ticked has varied; a Core Audio developer and an Apple Community answer both say it should be off for the clock source and on for the rest (snippet) — [coreaudio-api list](https://lists.apple.com/archives/coreaudio-api/2015/Jan/msg00063.html), [Apple Community](https://discussions.apple.com/thread/7499797), [MacRumors](https://forums.macrumors.com/threads/drift-correction-confusion.2383597)
- Loopback: current version listed as 2.4.10; reviews put the price at $99; the only latency figure found is one user's anecdotal 20 ms through a Loopback virtual device on Catalina (snippet) — [rogueamoeba.com/loopback](https://rogueamoeba.com/loopback/), [Tom's Guide](https://www.tomsguide.com/opinion/streaming-on-my-mac-shouldnt-require-this-amazing-dollar99-app-but-it-does), [reaper.blog review thread](https://reaper.blog/2018/12/loopback-2-review/)
- PC MASTER OUT (official): enable the PC MASTER OUT icon, then Preferences > Audio > Output channels > Master Output and pick the computer output device from the drop-down (snippet) — [Pioneer DJ troubleshooting guide PDF](https://www.pioneerdj.com/-/media/pioneerdj/downloads/other/troubleshooting/troubleshooting_001_e_v016.pdf)
- PC MASTER OUT + BlackHole (Pioneer forum guide for DDJ-RB, rekordbox 5.8.5, Catalina): set the virtual device as the system output, select the controller as rekordbox's audio device, tick the PC MASTER OUT box, and Master Output then reads "DDJ-RB + BlackHole 16ch" (snippet) — [Pioneer DJ forum: Streaming with OBS + DDJ-RB (Mac)](https://forums.pioneerdj.com/hc/en-us/articles/115005326586-Streaming-with-OBS-DDJ-RB-Mac)
- With an FLX4 and PC MASTER OUT on, Master Output reads "DDJ-FLX4 : MASTER + computer audio device"; with it off it reads "DDJ-FLX4 : MASTER"; the toggle is next to the settings cog at top right (snippet) — [We Are Crossfader FLX4 guide](https://wearecrossfader.co.uk/blog/getting-started-with-the-pioneer-dj-ddj-flx4/), [We Are Crossfader: stream from rekordbox with no soundcard](https://wearecrossfader.co.uk/blog/stream-from-rekordbox-with-no-soundcard/)
- A user reported the PC MASTER OUT path lagging while controller headphones stayed in sync; Pioneer's reply was that rekordbox is not the cause and to look for processing on the system output device or speakers (snippet) — [Pioneer community: Audio delay when PC Master Out selected](https://community.pioneerdj.com/hc/en-us/community/posts/22978707074841-RekordBox-Audio-Delay-when-PC-Master-Out-Selected)
- Aggregate route (Pioneer forum): macOS lets you combine interfaces into an aggregate device, select it in rekordbox's Audio settings with Mixer Mode internal, and assign master and headphones to different sub-device outputs under Preferences > Audio > Output Channels (answer given for a Focusrite 2i2, not a controller) (snippet) — [Pioneer community: Rekordbox Cue Sound Output](https://community.pioneerdj.com/hc/en-us/community/posts/22977946513561-Rekordbox-Cue-Sound-Output), [Pioneer forum: Headphone output to secondary soundcard](https://forums.pioneerdj.com/hc/en-us/community/posts/360052783412-Rekordbox-Headphone-Audio-Output-to-secondary-soundcard)
- One user guide claims the aggregate must be named exactly "Aggregate Device" (case sensitive) or rekordbox will not recognise it (single user report) (snippet) — [OBS forum thread](https://obsproject.com/forum/threads/cant-record-sound-rekordbox-blackhole.163101/)

### Inferences
Both procedures below are synthesised from the sources above and have not been tested with an FLX2.

Route A, PC MASTER OUT (best documented; processed audio leaves by a non-FLX2 output):
1. Install BlackHole 2ch; in Audio MIDI Setup set BlackHole 2ch and the FLX2 to the same sample rate.
2. Set macOS system output to BlackHole 2ch (PC MASTER OUT follows the computer's output device per the Pioneer/Crossfader guides). Side effect: all other system audio also lands in the effect chain, so move alert sounds to another device and quit other audio apps.
3. In rekordbox: Preferences > Audio > Audio = DDJ-FLX2; enable PC MASTER OUT; confirm Master Output reads "DDJ-FLX2 : MASTER + BlackHole 2ch" and Headphones Output is the FLX2 phones pair.
4. In the page: capture BlackHole 2ch with the section 1 constraints; create the AudioContext with `sinkId` set to the Mac's built-in output or a second DAC that feeds the speakers.
5. Leave the FLX2 MASTER jack unconnected, or use it as a dry zero-latency booth feed. Do not send the processed signal back to FLX2 channels 1-2 in this route: rekordbox is already playing the dry master there and Core Audio would sum the two, giving a dry + delayed-wet comb/flam.

Route B, Aggregate Device (processed audio leaves by the FLX2 MASTER jack; unverified):
1. Audio MIDI Setup: create an Aggregate Device containing DDJ-FLX2 (set as Clock Source, drift correction off) and BlackHole 2ch (drift correction on); same sample rate on both. If rekordbox does not list it, try the literal name "Aggregate Device".
2. rekordbox: Preferences > Audio > Audio = the aggregate, Mixer Mode = Internal; Output channels: Master Output = the BlackHole pair, Headphones Output = the FLX2 3-4 pair; PC MASTER OUT off.
3. Page: capture BlackHole 2ch; `sinkId` = DDJ-FLX2 (the raw device, not the aggregate); the default stereo destination lands on channels 1-2 = MASTER jack.
4. Verify the browser's output is not blocked by rekordbox holding the device (Core Audio normally allows shared access), and that rekordbox still recognises the FLX2 for Hardware Unlock when it is not the selected audio device.

- Route B is the cleaner result (one cable to the speakers from the controller, FLX2 master level knob still applies if it is analogue) but depends on two unverified rekordbox behaviours; Route A is close to officially documented but needs a second output device and hijacks the system output.
- A Multi-Output Device is not needed in either route; it would only be useful to mirror the dry signal to several devices, which is the opposite of what an insert needs.
- BlackHole 16ch offers no advantage here and, per the README, cannot act as a 2ch primary in some Multi-Output setups.

### Gaps
- Whether PC MASTER OUT can be made to send master only to the computer device (not duplicated to the controller) was not found; every source shows "controller MASTER + computer device".
- Whether PC MASTER OUT strictly follows the macOS default output or offers a device list on current rekordbox 7 is ambiguous between sources (official PDF mentions a drop-down; the forum guide sets the system output).
- No measured transfer latency for BlackHole or Loopback; the "zero" claim is the vendor's.
- BlackHole wiki pages on Aggregate Devices were not read (only the README).

## 6. Tempo sources reachable from a browser

### Takeaway
rekordbox does not send MIDI clock (repeated feature requests, staff reply "no timeline"), and its MIDI OUT mapping is LED feedback only. It does support Ableton Link, but a web page cannot join a Link session (UDP multicast), so a small local companion process is required to bridge Link to WebSocket or to MIDI clock (which Web MIDI can read). Link in rekordbox has reported limitations around following the master deck. The zero-dependency fallback is beat detection on the master audio the page is already receiving.

### Cited Findings
- MIDI clock out is not a feature of rekordbox; Pioneer staff: "Many users have requested this or Ableton Link, and our engineers are considering implementation, but we don't have a timeline or guarantee" (snippet; threads are old) — [Pioneer community: Virtual Midi Clock Send in Rekordbox](https://community.pioneerdj.com/hc/en-us/community/posts/22977420687001-Virtual-Midi-Clock-Send-in-Rekordbox), [Pioneer community: Midi clock/sync in rekordbox](https://community.pioneerdj.com/hc/en-us/community/posts/22976662468633-Midi-clock-sync-in-rekordbox), [Wolfmix forum](https://forum.wolfmix.com/viewtopic.php?t=1009)
- rekordbox MIDI mapping's MIDI OUT field is for sending LED/illumination feedback to controllers; no source shows BPM or beat data on MIDI OUT (snippet) — [DJ TechTools on rekordbox MIDI mapping](https://djtechtools.com/2016/02/03/rekordbox-4-0-6-midi-mapping-arrives-performance-pack/)
- Ableton Link in rekordbox: turn on [LINK] in the global section, then [LINK] on each deck to sync that deck to the Link BPM (deck BEAT SYNC buttons become LINK); a Link subscreen can be shown; not available when BPM exceeds +/-100% of tempo range or in DVS REL/ABS mode (snippet) — [rekordbox FAQ: Ableton Link](https://rekordbox.com/en/support/faq/ableton-link), [rekordbox 7.0.7 manual](https://cdn.rekordbox.com/files/20241213141602/rekordbox7.0.7_manual_EN.pdf)
- The Link BPM is controlled on the Link subscreen and needs MIDI mapping for hardware control (snippet) — [rekordbox FAQ operation hints](https://rekordbox.com/en/support/faq/operation-hints-6)
- Reported limitations: with LINK enabled the master deck concept effectively disappears; the Link value followed deck pitch in 6.5.3; users have asked for Link to follow the master deck ("Make Ableton Link bidirectional"); another report says rekordbox's Link cannot reliably pick up the downbeat of an already-playing master deck and tempo can only be changed from the other app or the rekordbox popup (snippet; user reports) — [Pioneer community: Make Ableton Link bidirectional](https://community.pioneerdj.com/hc/en-us/community/posts/22976380697753/comments/22984247507993), [NI community comment](https://community.native-instruments.com/discussion/comment/28596/)
- Plan availability: a 2020 rekordbox post lists Ableton Link support among Free-plan features for rekordbox 6 (snippet; not reconfirmed for v7) — [rekordbox.com 2020 plans guide](https://rekordbox.com/en/2020/05/subscription-plans-guide-core/), [rekordbox 6 launch post](https://rekordbox.com/en/2020/04/new-rekordbox-dj-application/)
- Browsers cannot join Link directly: Link discovers peers over UDP multicast and the web platform has no UDP, so projects use a local companion that joins the session and relays timing to the page (snippet) — [ricochet PR: Ableton Link sync via companion bridge](https://github.com/MohamedFekryyy/ricochet/pull/3)
- Existing bridges: `browser-sync-ableton-link` (Node.js server using the `abletonlink` library, browser clients schedule with Web Audio); `mpump` (browser sequencer with a separate Link Bridge companion app); YTbeatmakercues (Chrome extension with a local WebSocket bridge on port 20808) (snippet) — [vigliensoni/browser-sync-ableton-link](https://github.com/vigliensoni/browser-sync-ableton-link), [gdamdam/mpump](https://github.com/gdamdam/mpump), [YTbeatmakercues setup](https://deepwiki.com/jrucho/YTbeatmakercues-v2/1.2-installation-and-setup)
- A free "Link to MIDI Bridge" app converts a Link session to MIDI clock; one user reported the derived clock running a few BPM fast on their hardware (snippet) — [ADSR Sounds](https://www.adsrsounds.com/uncategorized/a-new-free-app-bridges-ableton-link-and-midi/), [Morningstar forum](https://forum.morningstar.io/t/midi-clock-sync-issue-ableton-link-link-to-midi-bridge/11767)
- `rkbx_link` reads transport position and beatgrid directly from rekordbox's process memory and outputs Ableton Link, OSC and sACN (not MIDI clock or WebSocket) at a default 120 Hz with a `delay_compensation` setting; Windows is the supported platform (free evaluation offsets for 7.2.2, paid licence for newer, up to 7.2.19); macOS is community-supported, "somewhat experimental", Apple Silicon only (7.2.8, 7.2.17, 7.2.18); repository is GPL-3.0 (fetched) — [grufkork/rkbx_link](https://github.com/grufkork/rkbx_link)
- Beat Link Trigger can emit MIDI clock or join a Link session, but it reads Pro DJ Link from CDJ/XDJ hardware, and rekordbox itself can only be Pro DJ Link tempo master in Export mode over Ethernet (snippet) — [DJ TechTools: Pro DJ Link secret features](https://djtechtools.com/2018/10/08/pro-dj-link-5-secret-features-of-pioneer-djs-protocol/)
- One user describes a chain "Ableton link on - Rekordbox translate it into midi clock - LoopMidi" (ambiguous single report; conflicts with the no-MIDI-clock evidence) (snippet) — [Algoriddim community](https://community.algoriddim.com/t/ableton-link-fails-in-5-6-7-release/42754)

### Inferences
- Workable tempo chain on macOS: rekordbox [LINK] on -> local bridge (Node `abletonlink` over WebSocket to the page, or Link-to-MIDI-clock into an IAC virtual port read with Web MIDI at 24 PPQN). The page hosted on GitHub Pages (HTTPS) connecting to `ws://localhost` is generally permitted by Chrome as a potentially trustworthy origin, but that and any Private Network Access prompt should be verified (not sourced).
- Catch: in rekordbox, Link is the tempo authority that decks follow, rather than a broadcast of whatever the master deck is doing. A DJ who beatmatches by hand with the pitch faders (the normal FLX2 workflow) would not be publishing deck tempo to Link, so Link gives a useful clock only if the DJ agrees to play with decks slaved to Link.
- For manual-beatmatch workflows the realistic options are (a) tap tempo / manual BPM entry in the page, (b) onset/beat tracking on the incoming master audio in the worklet (free, already in the signal path, but slow to lock and wrong during breakdowns), or (c) rkbx_link -> Link/OSC -> local bridge, which gives true beatgrid phase but is experimental on macOS, version-locked to rekordbox builds and relies on memory reading.
- Any tempo-synced effect must offset its phase by the insert latency N only if it is aligned to an external clock; effects driven by the audio itself are inherently aligned.

### Gaps
- Could not confirm from rekordbox.com whether Ableton Link is available on the rekordbox 7 Free plan with an FLX2 (the plans FAQ at [rekordbox.com plans-7](https://rekordbox.com/en/support/faq/plans-7/) was unreachable).
- Whether current rekordbox 7.2.x publishes the master deck's tempo and phase into the Link session is unresolved (conflicting old forum reports).
- No authoritative statement from AlphaTheta in 2025-26 about MIDI clock output; the "not a feature" evidence is from forum threads of unknown date.
- Did not verify the publisher or current availability of "Link to MIDI Bridge", or macOS equivalents.

## 7. The cue/master latency problem and what added latency is acceptable

### Takeaway
In this design the DJ's headphones (cue, and master-in-headphones if selected in rekordbox) stay un-delayed and pre-effect, while the room hears the master N ms later through the effect. Beatmatching done entirely in headphones is therefore unaffected; what suffers is the feel of anything judged against the speakers (scratching, fader cuts, effect knob moves) and any mix done "one ear on the monitor". Published guidance clusters around under ~10 ms as ideal and tens of ms as tolerable for non-scratch control; dedicated digital hardware sits at roughly 1.5-6 ms, so a 10-25 ms browser insert is several times worse than hardware but inside what DJ software itself considers usable.

### Cited Findings
- Mixxx's manual guidance: a latency between 36-64 ms is acceptable when using keyboard/mouse or a MIDI controller; below 16 ms is recommended for vinyl control (snippet) — [Mixxx wiki manual](https://github.com/mixxxdj/mixxx/wiki/manual)
- Mixxx implemented an adjustable headphone-output delay precisely so headphone timing can be matched to a later main output; the request proposed expressing it as distance (delay = distance / speed of sound), i.e. the same compensation DJs need for far-away PA speakers (snippet) — [Mixxx bug 225966: Adjustable headphone latency](https://bugs.launchpad.net/bugs/225966)
- Mixxx also had (and fixed in 1.10) a delay between streams when headphones and master are on different sound cards, and its current manual says that with multiple interfaces the engine is clocked by the main output with selectable synchronisation for the others (snippet) — [Mixxx bug 726894](https://bugs.launchpad.net/bugs/726894), [Mixxx manual: Sound Hardware](https://github.com/mixxxdj/manual/blob/2.4/source/chapters/preferences/sound_hardware.rst)
- Digital mixer reference points from live-sound forums: an inserted digital device adds about 1.5-2.0 ms at 48-96 kHz plus its own processing latency; one DSP platform is cited with a fixed latency of about 5.8 ms (snippet; anecdotal) — [Speakerplans forum](https://forum.speakerplans.com/digital-mixer-delay-lag_topic97458.html), [Harmony Central forum](https://www.harmonycentral.com/forums/topic/188667-compact-digital-mixer-latency-for-analog-quotinsertsquot/)
- A DJ-oriented article recommends total round-trip below 10 ms and says buffers above 256 samples (over ~10 ms) can disrupt beat juggling and rapid cueing; its per-device table (e.g. DJM-A9 under 2 ms) is unsourced (snippet; low authority) — [moldstud.com](https://moldstud.com/articles/p-navigating-latency-issues-with-dj-effects-processors-tips-for-seamless-mixing)
- rekordbox precedent: with PC MASTER OUT a user heard the second output lag while the controller headphones stayed in sync, and a third-party guide advises doing all monitoring in the controller's headphones (cue plus master) rather than by ear from a delayed output; duplicating audio to a second sound card is called a last-resort workaround because of the latency difference (snippet) — [Pioneer community thread](https://community.pioneerdj.com/hc/en-us/community/posts/22978707074841-RekordBox-Audio-Delay-when-PC-Master-Out-Selected), [startingtodj.com headphones guide](https://startingtodj.com/rekordbox-headphones-issues-how-to-fix-them/), [startingtodj.com speakers guide](https://startingtodj.com/connecting-speakers-to-ddj-400-problems-solved/)

### Inferences
- Physical scale: at about 343 m/s, 10 ms equals 3.4 m and 20 ms equals 6.9 m of speaker distance. A 20 ms insert therefore sounds to the DJ like standing about 7 m further from the PA, a situation club DJs already handle by mixing in headphones or with a booth monitor. This is the strongest argument that a 10-25 ms master insert is workable for mix DJing.
- Coping strategies, in order of practicality for an FLX2: (1) beatmatch entirely in headphones using cue + master cue in rekordbox (both pre-effect and time-aligned); (2) use the FLX2's own dry MASTER jack as a zero-latency booth monitor (Route A) and accept that the room is N ms behind; (3) if the DJ software offers it, delay the headphone bus by N to re-align (Mixxx can; no evidence rekordbox can); (4) keep N small (128 or 64 frame quantum, matched sample rates, no look-ahead effects).
- Use cases that are not acceptable at 15-25 ms: scratching or fast crossfader cuts judged from the main speakers, and one-ear monitor mixing where the open ear hears the delayed PA. With an FLX2 (entry-level, small rooms) the DJ is usually close to the speakers, so the flam between headphone master and room master will be audible when monitoring master in headphones at low volume; it is not audible to the audience.
- The DJ never hears the effect in the headphones in this topology (cue path bypasses the browser), so effects must be auditioned from the room or a booth monitor fed from the browser output. Sending a copy of the processed signal to headphones is not possible without also moving the cue mix into the browser.
- Planning threshold suggested by the sources: under 10 ms is indistinguishable from hardware in practice, 10-20 ms is fine for blend mixing, 20-40 ms is usable but noticeable on transients, above about 40 ms is a problem.

### Gaps
- No manufacturer-published latency for Pioneer/AlphaTheta RMX-1000/RMX-IGNITE, DJM-series send/return, or other external DJ FX units was found; the hardware figures above are forum anecdotes about live-sound consoles.
- No source found for a headphone/master delay-compensation setting in rekordbox.
- No controlled study of DJ tolerance to master-only latency was found; the thresholds are extrapolated from monitoring-latency guidance.

## 8. Alternatives: native AU/VST hosting and Windows equivalents

### Takeaway
The same virtual-device topology works with a native plugin host in place of the browser and would avoid the browser's capture/output buffering and cross-device bridging, at the cost of losing the zero-install web deployment. On Windows the equivalents are VB-Cable/VoiceMeeter, where the virtual cable itself can add 14-21 ms unless ASIO paths are used.

### Cited Findings
- VB-Audio: a 256-sample buffer at 44.1/48 kHz is about 5 ms, "basically the minimum latency we can expect to manage reliable from the Windows Operating System" (snippet) — [voicemeeter.com: How to optimize your latency](https://voicemeeter.com/?p=235265)
- VB-Cable's added delay depends on its internal buffer: a 2048-sample internal buffer gives up to about 21.3 ms at 48 kHz, with one estimate nearer 14.2 ms when the client apps use small buffers; VB-Cable is "just a pipe between two apps", and Voicemeeter's virtual ASIO driver is suggested for lower latency (snippet; forum posts) — [VB-Audio forum](https://forum.vb-audio.com/viewtopic.php?p=2392), [VB-Audio forum](https://forum.vb-audio.com/viewtopic.php?p=4745)
- Voicemeeter Banana exposes an "Insert Virtual ASIO" device (described as 22-in/22-out) and virtual ASIO devices that can serve up to four client apps (snippet) — [AV Watch (Impress) review](https://av.watch.impress.co.jp/docs/series/dal/1270953.html), [VB-Audio Voicemeeter Banana](https://vb-audio.com/Voicemeeter/banana.htm)
- On Windows rekordbox addresses the controller as "DDJ-FLX4 WASAPI", and older Pioneer forum advice uses ASIO4ALL to combine several sound cards so master and headphones can be assigned under Preferences > Audio > Output Channels (snippet) — [rekordbox FAQ](https://rekordbox.com/en/support/faq/operation-hints-6), [Pioneer forum: Headphone output to secondary soundcard](https://forums.pioneerdj.com/hc/en-us/community/posts/360052783412-Rekordbox-Headphone-Audio-Output-to-secondary-soundcard)
- BlackHole exists to pass audio between applications "with zero additional latency", which applies equally to a native host reading it (fetched) — [BlackHole README](https://github.com/ExistentialAudio/BlackHole)

### Inferences
- Native host option on macOS (general knowledge, not researched or sourced in this pass): any AU/VST host that can take BlackHole as input and the FLX2 as output (for example via an Aggregate Device so both sit in one clock domain and one I/O callback) can run at 32-64 sample buffers, which would plausibly put the insert at roughly 3-8 ms instead of 10-25 ms. Candidate hosts and system-audio tools exist (AU Lab, Hosting AU, Element, Gig Performer, Ableton Live, Rogue Amoeba Audio Hijack/SoundSource), but none was verified here.
- A middle path that keeps the web codebase: compile the DSP to WASM once and wrap the same core as an AU/VST (or ship the page in an Electron/Tauri shell). A shell still uses Chromium's audio stack, so it does not by itself reduce latency.
- Windows is less favourable for the browser approach: Chrome uses WASAPI shared mode (about 10 ms device period, per the historical figure in section 2), VB-Cable adds its own buffer, and rekordbox's WASAPI device is the controller. Expect a noticeably higher N than on macOS unless VoiceMeeter's ASIO insert and a native host are used.

### Gaps
- No sources gathered on specific macOS AU/VST hosts, their minimum buffer sizes with aggregate devices, or measured insert latency; the native numbers above are estimates.
- No source on whether rekordbox for Windows lets a controller's WASAPI device be combined with a virtual cable other than via PC MASTER OUT.
- Chrome's current Windows output/capture buffer sizes and any exclusive-mode option were not researched.
